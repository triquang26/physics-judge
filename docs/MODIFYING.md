# Modifying kinescore

A how-to-modify guide: for each common change, which files to touch, which
tests to re-run, and which docs need updating afterward. See
[PROVENANCE.md](PROVENANCE.md) before touching anything under
`src/kinescore/robots/franka/fk.py`, `robots/gr1/fk.py`, or any file marked
**verbatim** there — those are ported bit-for-bit and a "cleanup" edit there
is a silent provenance break, not a refactor.

A note on the CLI: `pyproject.toml` declares a `kinescore` console script
(`kinescore.cli.main:main`, see `[project.scripts]`), and the README's
Quickstart shows `kinescore manifest`/`reference build`/`score`/`aggregate`/
`report` commands — but **`src/kinescore/cli/main.py` does not exist**
(`src/kinescore/cli/__init__.py` is an empty file, and that is the whole
package). Every row below therefore describes the underlying Python API
(`kinescore.bench.manifest`, `kinescore.bench.runner`,
`kinescore.reference.fingerprint`, `kinescore.core.scorer`) directly — that
API is complete and tested; only the CLI wrapper around it is missing.

| Change | Files to touch | Tests to re-run | Docs to update |
|---|---|---|---|
| **Change the backbone** (new DINO variant, different `patch_pool`, a non-DINO encoder) | `src/kinescore/backbones/dino.py` (`FeatureBackbone`) or a new sibling module implementing the same `.encode(rgb) -> (N,V,P,D)` contract; `src/kinescore/backbones/pooling.py` if the pooling itself changes | `tests/test_head_golden.py` (backbone feeds the head — verify the golden fixture's downstream numbers still match if this is meant to be a no-op change); any `@pytest.mark.net`/`ckpt` test that loads a real backbone | None structurally required, but if you change what a checkpoint's `cfg["backbone"]` dict means, update `readers/checkpoint.py`'s docstring and re-check `docs/PROVENANCE.md`'s note on `backbones/dino.py` being **adapted**, not verbatim (the `encode_latent` deletion is already documented there — a new backbone type is a new addition, not a further deletion) |
| **Retrain a head** (new weights for `AttentivePoseHead`, `ReadoutV2Head`, etc.) | Training code lives outside this package (`src/kinescore/training/__init__.py` is an empty stub — see the row below); once trained, save via `readers/checkpoint.py::save` (for `AttentivePoseHead`) so `hidden`/`dropout`/`view_layout_key`/`robot_name`/`limit_semantics` all round-trip (defect D5) | `tests/test_checkpoint_roundtrip.py`, `tests/test_checkpoint_legacy_cfg.py` (if you touch the save/load format itself); `@pytest.mark.ckpt`-gated `tests/test_real_production_checkpoints_load` if you have `$KINESCORE_CIASC_ROOT` set, to make sure the three real checkpoints still load | If `hidden`/`n_heads`/`embed_dim` inference-from-weights logic changes, update the D5 section of `docs/PROVENANCE.md` |
| **Add a camera view** (2-view or N-view instead of 1/3) | `src/kinescore/core/clip.py::ViewLayout` already supports arbitrary `n_views` — no change needed there. Construct readers/backbones with the right `ViewLayout(n_views=N, tokens_per_view=P)`; if a *new head family* needs multiview support it never had, compose `src/kinescore/heads/views.py::ViewEmbedding` in front of it (zero-init, so `n_views=1` stays a no-op) rather than adding an ad hoc `if n_cams > 1` branch | `tests/test_multiview_layout.py` (both directions — too-few and too-many tokens — must still raise for any new layout combination you exercise) | `README.md`'s "Supported robots" table lists camera counts per robot — update if a robot's supported view count actually changes (README is out of scope for this task, note only) |
| **Change frame rate** (score at a different fps, or support variable-fps sources) | Nothing in `src/kinescore/core/clip.py` needs changing — `ClipSpec.from_fps`/`.subsample` already handle any rate. If a new *discovery source* needs a frame-rate override, add a `fps_hint` to its `DiscoveredClip` entries in a `bench/manifest.py` plugin; `video/probe.py::resolve_timebase` cross-checks it against the probed rate automatically | `tests/test_clip_timebase.py`, `tests/test_dt_invariance.py`, `tests/test_metric_registry_conformance.py` (every metric's `dt_exponent` is re-verified against the new arithmetic if you touch `metrics/ops.py::fd`), `tests/test_video_probe.py`, `tests/test_reference_dt_roundtrip.py` (if scoring against an existing reference at a different rate — expect `RateMismatchError` unless you rebuild the reference at the new rate) | If you add a *new* `DtSource` value (currently `ffprobe`/`fps_arg`/`dt_arg`/`table`/`synthetic`), update `core/clip.py`'s `DtSource` Literal and `docs/SCHEMA.md`'s clip-record section |
| **Add a metric** | New file (or addition to an existing) under `src/kinescore/metrics/`, registered via `register(...)` at import time; add it to `metrics/__init__.py`'s side-effecting imports if it's a new module | See [ADDING_A_METRIC.md](ADDING_A_METRIC.md) in full — in short: `tests/test_metric_registry_conformance.py` (auto-parametrized, numerically verifies your declared `dt_exponent`), plus a metric-specific test file for edge cases (missing inputs, `min_frames` boundary, degenerate arithmetic → `NaN`-not-a-bare-float) | `docs/METRICS.md` (add the row — formula, units, `dt` exponent, direction, detects/does-NOT-detect); if you add it to `metrics/suites.py::INVARIANT_V1.invariant_keys`, see the "tune the PIS tolerance/floors" row below — **this changes `suite_id`**, which invalidates comparison with every prior run |
| **Add a robot** | New package under `src/kinescore/robots/<name>/` implementing the `RobotSpec` protocol (`core/robot.py`); register it in `src/kinescore/robots/__init__.py::_FACTORIES` (lazily-imported factory, so importing `kinescore.robots` never pulls in a new robot's heavy dependencies for callers who don't ask for it) | See [ADDING_A_ROBOT.md](ADDING_A_ROBOT.md) in full — in short: a `golden_fk_<robot>.npz` fixture, a rest-pose bone-length assertion test, a degenerate/actuated-bone check (D9), `tests/test_metric_registry_conformance.py` re-run against the new robot if it's used as `fixture_robot` anywhere | `README.md`'s "Supported robots" table (out of scope for this task); `docs/ADDING_A_ROBOT.md` if the *protocol itself* changes, not just a new implementation of it |
| **Tune the PIS tolerance/floors** (`DEFAULT_TOL`, `DEFAULT_FRAC_TOL`, `UNIT_FLOORS`) | `src/kinescore/reference/normalize.py` (`DEFAULT_TOL=3.0`, `DEFAULT_FRAC_TOL=0.1`) and `src/kinescore/reference/fingerprint.py` (`UNIT_FLOORS` dict — defaults only; `RealMotionReference.build` additionally fits a per-key median-absolute-deviation floor from the real data itself, so a key not in `UNIT_FLOORS` still gets a sane data-driven floor). Changing `tol`/`frac_tol` does **not** change `suite_id` (they're `invariance_score` call-time arguments, not suite structure) — every prior reference/run remains comparable, but the *absolute PIS numbers* from before and after the change are not | `tests/test_pis_zero_baseline.py` (the no-op guarantee: when `base > floor`, changing the floor must not move the PIS for well-conditioned keys — re-verify this still holds for your new floor values), `tests/test_reference_golden.py` | `docs/PROVENANCE.md`'s D3b section if the floor-fitting *algorithm* changes (not just a constant); no change needed to `docs/METRICS.md` unless a metric's tolerance treatment (`*_frac` absolute vs. relative) changes |
| **Regenerate goldens** | `tools/gen_golden.py` (add/modify a `golden_*` generator function, register it in `GENERATORS`); needs both source checkouts (`--source-a`, `--source-b`) reachable — see the note in `provenance/git_state.json` about B's `.git` being a dead worktree pointer, which does not block *reading files*, only `git` metadata | See [REGENERATING_GOLDENS.md](REGENERATING_GOLDENS.md) in full — the governing rule is: **every intentional behaviour change ships both a `*_legacy` and a `*_v2`-equivalent fixture/assertion plus a PROVENANCE row; a golden that differs with no paired fixture means the port is wrong, not the golden stale** | `tests/golden/MANIFEST.json` is regenerated automatically by the script; update `docs/REGENERATING_GOLDENS.md` only if the governing rule itself changes, and `docs/PROVENANCE.md`'s (d) section if `tools/ast_diff.py`'s self-test coverage changes |
| **Upgrade torch** | `pyproject.toml`'s `dependencies = ["torch>=2.5,<3", ...]` pin; re-run the full test tier, since `tests/golden/*.npz` were generated under `torch==2.7.1` (`tests/golden/MANIFEST.json::versions`) with `torch.use_deterministic_algorithms(True)` — a torch upgrade can shift bit-level results even when the *arithmetic* is unchanged | The full suite, especially every golden-fixture-comparison test (`test_fk_parity_franka.py`, `test_head_golden.py`, `test_reference_golden.py`, `test_checkpoint_roundtrip.py`'s `ckpt`-marked cases) — a small numeric drift here is a torch-version artifact to investigate, not necessarily a regression, but it must be understood before merging | `tests/golden/MANIFEST.json`'s `versions.torch` field is the record of what a fixture was generated under; if tolerances need loosening for a new torch version, document why in the affected test file, not silently |
| **Add a dataset** (new video source for the manifest) | New `SourcePlugin` (zero-arg callable yielding `DiscoveredClip`) passed to `bench/manifest.py::build_manifest` — do **not** add a new `if family == ...` branch inside `build_manifest` itself; that hardcoded-cascade pattern is exactly what this module's plugin design replaced (see its module docstring) | `tests/test_manifest.py` (add a plugin-specific test alongside existing ones); `tests/test_video_probe.py` if the new source needs a novel `fps_hint`/timebase resolution path | None required unless the new source needs a new `ROW_KEYS` column, in which case update `docs/SCHEMA.md`'s manifest-row description (if one exists there) and `bench/manifest.py`'s own `ROW_KEYS` docstring |
